# "다시, 말해" (say-it-again) — 프로젝트 계획

> 역할·스택은 화면 설계(`docs/wireframe.webp`) 기준으로 조정됨. 데이터 형태의 최신 기준은 `docs/api.md`.
> 1·9·10·11절은 해커톤 당시의 계획 기록이다. 3~8절은 지금 코드에 맞춰 둔다.

## 1. 행사 개요 및 규칙
- 행사: 2026 제1회 컴퓨터공학과 해커톤 L/NKerthon (건국대 글로컬캠퍼스)
- 개발 가능 시간: 10/1(목) 19:30 ~ 10/2(금) 11:30 (16시간). 기능 코드 커밋은 19:30 이후.
- 발표: 10/2(금) 13:30~14:30, 팀당 발표+시연+질의응답 총 6분 내외 (실제 시연 3~4분)
- 발표자료(PDF/PPT) 필수 구성: ① 문제 정의 및 주제 연관성 ② 아이디어 및 해결 방안 ③ 주요 기능 및 구현 방법 ④ 결과물 및 시연 ⑤ 기대 효과 및 활용 방안
- 심사(100점): 주제 적합성/문제 정의 20, 창의성/차별성 20, 기술 구현/완성도 30, 실용성/발전 가능성 20, 발표/질의응답 10. 동점 시 기술 구현 → 창의성.
- 주제: "우리가 바꾸는 캠퍼스의 하루"
- 규칙: 생성형 AI·코딩 도구 허용. 외부 API/오픈소스는 발표에서 명시. 표절·대리 개발 금지. 시연 영상/캡처 백업 권장.

## 2. 프로젝트 정의
- 한 줄 소개: 대학생의 말하기 연습을 AI가 진단. 어디서 버벅였는지, 왜 막혔는지, 어떻게 다시 말하면 좋은지까지 알려준다.
- 문제: 강의 발표, 어학 스피킹, 면접을 혼자 연습할 때 피드백해줄 사람이 없다. 기존 앱(Orai, Speeko, Speak AI, SayNow AI 등)은 필러워드 횟수 같은 수치에서 끝난다.
- 차별점: 침묵·정체 구간(패닉존)을 타임스탬프로 잡고, LLM이 그 구간의 문맥을 보고 "왜 막혔는지" 진단하며 대안 대본까지 제시. 대본 위에 문제 지점을 직접 하이라이트.
- 포지셔닝: 문제정의는 "대학생활의 말하기 3대 순간(강의 발표 / 어학 스피킹 / 면접)". 계획 당시에는 시연을 "강의 발표" 모드 하나로 고정하고 나머지를 확장성으로 설명하려 했고, 지금은 세 모드가 모두 구현되어 있다.

## 3. 입력 모드
mode: presentation | speaking | interview (요청·응답 상세는 `docs/api.md`)
- 발표(`presentation`): language는 `ko` 또는 `en`. `level`은 assignment(과제 발표) | exam(시험 발표) | keynote(큰 강연). 5분 단위 녹음 파일을 최대 5개 보낸다. `level`은 LLM 프롬프트에 함께 전달한다. 발표 자료(PDF)는 화면에 보여 주는 용도이며 서버로 보내지 않는다.
  - 발표 예상 질문 답변: 결과 화면에서 받은 예상 질문에 답하는 연습. 같은 발표 모드에 `questions`를 붙여 보내면 서버가 발표 질의응답 기준으로 평가한다.
- 어학 스피킹(`speaking`): language는 `en` 고정. `exam`은 TOEIC-Speaking | opic. 질문 5개는 서버가 LLM으로 만들고(`POST /api/questions`, 토익 Part 2 사진은 이미지 생성), 실패하면 프론트의 기본 문항을 쓴다. 질문별 답변 녹음을 최대 5개 보내고 질문 문자열을 `questions`로 함께 보낸다.
- 면접(`interview`): language는 `ko` 또는 `en`. 지원 직무를 적으면 서버가 맞춤 질문 5개(자기소개·지원 동기·직무·경험·마무리)를 만든다. 질문별 답변 녹음을 보낸다.
- 모드별로 필러워드 사전, 패닉존 기준, LLM 평가 기준을 바꾼다.
  - 필러워드: 확실한 군말(ko: 어/음/아, en: um/uh/er)은 항상, 애매한 말(ko: 그/저/이제/막/그러니까, en: like/so/well/actually)은 바로 뒤에 0.3초 이상 멈칫했거나, 다른 군말 바로 뒤이거나, 바로 되풀이했을 때만 필러로 본다.
  - 패닉존: 발표·면접은 2초, 스피킹은 1.5초 이상 정지. 질문에 답하는 경우(스피킹·면접·발표 예상 질문 답변)는 첫마디 전 3초 이상 침묵도 패닉존.
  - 발표: 구어체 적합성, 문장 길이, 구조 (`level`별 기준은 프롬프트로 전달)
  - 스피킹: 질문 적합성, 문법·어휘 정확성
  - 면접: 질문 의도, 두괄식, STAR, 구체성, 직무 연결
  - 문법 항목은 스피킹과 영어 면접에서만 본다.

## 4. 핵심 플로우
API는 아래와 같다 (`docs/api.md`).
1. (스피킹·면접) `POST /api/questions`: 처음 질문 5개 생성. 토익은 `POST /api/questions/image`로 Part 2 사진을 뒤에서 따로 받는다
2. `POST /api/transcribe`: 녹음 파일 1~5개 → 파일마다 병렬 STT(단어 타임스탬프, 질문 내용을 힌트로) → 파트별 문장 단위 분할 + 패닉존(pause 줄) 삽입 → 대본 응답
3. 사용자가 대본을 보고 전사 오류(문장 안 단어)만 고친다
4. `POST /api/analyze`: 고친 대본 → 필러워드/중복 단어/패닉존 탐지(코드) → 파트별 LLM 병렬 호출(번호 붙은 스크립트)로 원인 진단 + 최종 대본 + 표현 개선 + (질문에 답하는 경우) 코멘트·정확성 → 합산(`charts`, `analysis`) → 총평 LLM 1회 호출(파트별 요약만 입력) → 스크립트 하이라이트 → 총평 화면
5. `POST /api/retry` ("다시, 말해" 재도전): 다시 녹음한 대본 → 코드 분석 → 이전 결과와 전후 비교 + 대본 일치율 → 재도전 총평 LLM 1회
6. `POST /api/questions` (꼬리질문): 결과 화면에서 버튼을 누르면 실제로 말한 내용으로 질문 1~3개 생성 → 그 질문으로 다시 연습
7. `GET /api/health`: 서버 상태 점검

녹음 파일 하나가 응답의 `parts` 하나가 된다. 서버는 아무것도 저장하지 않는다.

## 5. 스크립트 데이터 구조
서버가 단어 사이 간격(gap)을 계산해 직접 만든다.

### 5-1. 분할 규칙 (한 줄 = 한 문장)
| 조건 | 처리 |
|---|---|
| 문장 끝 (whisper segment 끝, 문장부호 . ? !) | 줄바꿈 |
| 단어 사이 2초(스피킹은 1.5초) 이상 정지 | 문장 중간이라도 줄바꿈 + pause 줄 삽입 (패닉존) |
| 첫마디 전 3초 이상 침묵 (스피킹·면접·발표 예상 질문 답변만) | 대본 맨 앞에 pause 줄 삽입 |
| 한 문장 40단어 초과 | 줄바꿈 (안전장치) |
- 발표 본편은 녹음 맨 앞 침묵을 무시한다. 맨 뒤 침묵은 모든 모드에서 무시한다.
- whisper가 침묵을 앞뒤 단어에 붙이곤 해서, 1.5초보다 긴 단어는 1.5초로 자른 뒤 멈춤을 잰다.
- 상수 PANIC_GAP=2.0, SPEAKING_PANIC_GAP=1.5, LEAD_PANIC_SEC=3.0, MAX_WORD_SEC=1.5, MAX_WORDS=40 (`backend/src/config.ts`) — 실제 샘플로 튜닝.

### 5-2. 데이터 형태
`docs/api.md`의 `Line[]`(`{start, end, offset, words, wordTimes?, pause?}`)을 기준으로 한다. 하이라이트는 파트 전체 단어 번호 범위(`from`~`to`)로 표시하므로 문장을 넘는 구·절도 표시할 수 있다. 줄 안의 단어 `i`의 번호는 `offset + i`다.

### 5-3. 렌더링 · LLM 입력
- pause 줄은 "⏸ N.N초 정지" 마커. 바로 앞 문장의 마지막 3단어를 패닉존 하이라이트(대본 맨 앞 pause 줄은 바로 뒤 문장의 처음 3단어). 마커 클릭 시 원인과 대안 대본 표시.
- LLM에는 번호 붙은 입력을 준다:
  ```
  [0] 0:동해물과 1:백두산이 2:마르고 3:닳도록
  [1] (패닉존 3.2초)
  [2] 0:하느님이 1:보우하사 ...
  ```
  응답 후 범위를 벗어난 인덱스는 폐기.

## 6. 화면 구성
### 6-1. 스크립트 하이라이트 (5색, 색 + 밑줄 모양 병용)
| 색 | 의미 | 대상 | 스타일 |
|---|---|---|---|
| 빨강/주황 | 막힌 지점 | 패닉존 직전 구간 | 진한 배경 + 굵은 실선 |
| 노랑 | 군더더기 | 필러워드(낱개 얇은 밑줄), 필러 몰린 문장(연한 배경) | |
| 보라 | 반복 | 중복 단어 | 물결 밑줄 |
| 파랑 | 표현 개선 | 모호·약한 표현, 문어체, 부정확한 어휘 | 점선 밑줄 |
| 초록 | 문법 | 문법 오류 (스피킹·영어 면접만) | 이중 밑줄 |
- 세부 유형은 툴팁 라벨과 상단 칩 필터로 구분.
- 겹칠 때 배경색은 최상위 1개(빨강>노랑>보라>파랑>초록), 나머지는 밑줄 + 툴팁 "이슈 N개".
- 기본은 빨강+노랑만 켬, 나머지는 칩으로. 프로젝터 대비 밑줄 모양·두께로도 구분.
- 표현 개선은 영향도 순으로 파트당 최대 8개. 패닉존은 긴 상위 3~5개 강하게, 나머지 옅게.
- 중복 단어: ① 같은 말(1~3단어)을 바로 반복하면 묶어서 표시. ② 공백 분리 후 끝 조사 정규식 제거, 5문장 윈도우에서 같은 어간 3회 이상이면 플래그. 필러와 흔한 말은 제외.
- 화면 용어는 패닉존·군말·반복·표현 개선·문법·정상으로 통일한다 (서버가 쓰는 설명 글도 같은 이름만 쓴다).

### 6-2. 총평 화면
데이터는 `docs/api.md`의 `charts`, `analysis`, `parts[].final`.
1. 카테고리 비율 차트: 패닉존·군말·반복·표현 개선·문법·정상 단어 6개 (`charts.categoryRatio`)
2. 중복 단어 차트, 보라색 (`charts.repeatTop`)
3. 필러워드 차트, 노란색 (`charts.fillerTop`)
4. 분석 총평 (`analysis`): 점수, 핵심 지표(WPM, 필러 수, 패닉존 횟수·총 정지 시간 등), 한 줄 총평, 가장 먼저 고칠 3가지, 전체 코멘트(`summary.comment`)
   - 점수 = 말하기 습관 점수(100 − 패닉존·군말·반복 비율). 표현 개선·문법은 LLM이 정해 실행마다 달라질 수 있어 감점하지 않는다.
   - 질문에 답하는 경우(스피킹·면접·발표 예상 질문 답변)는 답변 정확성(LLM, 토익 Part 1은 지문 일치율)과 가중 기하평균으로 합친다 (정확성 비중: 스피킹 0.5, 면접·발표 예상 질문 답변 0.7).
5. 최종 대본: 파트별 수정 대본 (`parts[].final`, 면접·발표 예상 질문 답변은 모범 답안, 토익 Part 1은 없음)
6. "다시, 말해" 재도전: 같은 내용을 다시 녹음해 이전 결과와 전후 비교 (점수, 분당 군말·패닉존·반복, 대본 일치율, 재도전 총평)
7. 꼬리질문: 버튼을 누르면 실제로 말한 내용으로 질문 1~3개 (발표는 청중 예상 질문, 스피킹은 추가 연습 질문, 면접은 답변을 파고드는 질문)

## 7. 기술 스택
- frontend: React(Vite) + TypeScript + TailwindCSS + DaisyUI, react-router, MediaRecorder(webm, Safari는 mp4), recharts, pdfjs-dist(발표 자료 미리보기), 브라우저 음성 합성(질문 읽어 주기). 모바일 우선 반응형. 연습 기록은 브라우저 localStorage에 남긴다(최대 20개).
- backend: Node.js + Express + TypeScript(tsx), multer, cors, dotenv
- STT: `openai` 패키지, whisper-1, timestamp_granularities ["word","segment"], response_format verbose_json. webm·mp4 그대로 전송. 군말을 지우지 않도록 군말 예시를, 고유명사를 맞게 받아 적도록 질문 내용을 힌트로 준다.
- LLM: OpenAI API (`openai` 패키지), Structured Outputs(strict JSON schema)로 구조화 JSON. 모델은 환경 변수 `OPENAI_LLM_MODEL`, 추론 강도 `low`, 호출당 제한 45초·재시도 1번.
- 이미지: OpenAI 이미지 생성(`OPENAI_IMAGE_MODEL`, gpt-image-2.5-flare)으로 토익 Part 2 사진. 제한 60초, 실패하면 프론트 기본 사진.
- 저장: DB 없음. 로컬 실행, 모바일 필요 시 ngrok(https). 요청 출처(Origin)는 localhost·사설 IP·ngrok만 기본 허용(`CORS_ORIGIN`으로 추가).
- mock 모드: `MOCK_STT`, `MOCK_LLM`을 켜면 `backend/fixtures/`의 저장된 응답으로 키·네트워크 없이 동작 (시연 백업).

## 8. LLM 응답 스키마
LLM 호출은 아래 종류가 있다 (모두 `backend/src/llm/`, 프롬프트는 `prompts.ts`).

| 호출 | 언제 | 횟수 |
|---|---|---|
| 파트 분석 | analyze | 녹음 파일(파트)마다 병렬 1회 |
| 총평 | analyze | 파트별 요약만 받아 1회 |
| 재도전 총평 | retry | 전후 비교 수치와 새 패닉존 문맥으로 1회 |
| 정확성 채점 | retry (이전 정확성을 보냈을 때만) | 파트마다 병렬 1회 (토익 Part 1은 코드로 계산) |
| 질문 생성 | questions | 면접 / 토익 / 오픽 처음 질문, 꼬리질문 각 1회 |

파트 분석 (입력: 번호 붙은 스크립트 + 모드·`level`·`exam`·질문 문자열). 아래 순서로 생성한다:
```json
{
  "panics": [{ "line": 3, "reason": "왜 막혔는지", "fixed": "대안 대본" }],
  "final": ["수정된 문장", "..."],
  "issues": [{ "line": 2, "from": 3, "to": 4, "category": "expression|grammar", "reason": "...", "fixed": "..." }],
  "comment": "...",
  "accuracy": 80
}
```
- `panics[].line`은 패닉존(pause) 줄 번호다. 패닉존 위치·`pauseSec`는 코드가 이미 정했고, 서버가 같은 pause 줄의 panic 하이라이트에 `reason`·`fixed`를 채운다.
- `final`을 `issues`보다 먼저 쓰게 한다. `issues`의 `fixed`는 `final` 안의 구절을 글자 그대로 복사하게 지시하고, `final`에 없는 표현을 주면 서버가 그 하이라이트를 버린다.
- `issues`의 `line`, `from`, `to`는 입력의 줄 번호와 줄 안 단어 번호이고, 서버가 `offset`을 더해 파트 전체 단어 번호로 바꾼다. 범위를 벗어나면 폐기한다. 범위는 바꿔야 할 단어만 최소로(보통 1~4단어) 잡게 지시한다.
- `grammar`는 스피킹과 영어 면접에서만 받는다. `comment`와 `accuracy`(0~100)는 질문에 답하는 경우(스피킹·면접·발표 예상 질문 답변)에만 쓴다. 토익 Part 1(지문 읽기)은 `final`을 빈 배열로 돌려준다.
- 면접·발표 예상 질문 답변의 `final`은 평가 기준에 맞게 다시 짠 모범 답안이다.
- 서버가 쓰는 설명 글의 "필러"는 화면 용어 "군말"로 한 번 더 바꾼다.

총평:
```json
{ "headline": "...", "topPriorities": ["...","...","..."], "comment": "..." }
```
재도전 총평: `{ "improved": ["..."], "remaining": ["..."], "comment": "..." }`

- 필러·중복은 코드가 찾으므로 LLM에 요청하지 않는다. 표현 개선은 파트당 최대 8개로 명시한다.
